# 법인 뉴스 이슈 트래커 — 기능 명세

기준일: 2026-09-17. 이 문서는 현재 코드·설정의 동작과 운영 절차를 정의한다. 추가 요구와 미결정 정책은 11절에 모은다. 구현이 있다는 사실은 운영 검증이나 정책 승인을 뜻하지 않는다.

## 1. 목적과 범위

### 1.1 목적

S&T 법인금융상품실 영업 담당자가 법인 미팅 전에 확인할 뉴스를 수집하고, 신규법인·팀별 엑셀로 제공한다. 결과는 영업 검토 자료이며, 거래 사실이나 상품 적합성을 확정하는 자료로 사용하지 않는다.

### 1.2 제공 기능

- 업무망 엑셀에서 법인명·팀을 추출할 VBA 코드 생성
- 법인명과 영업 키워드로 지정 기간의 뉴스 검색
- 기존 법인 이슈 선별과 신규 법인 후보 추출
- 담당자의 LLM 검토 결과 병합
- 신규법인 및 1~6팀 시트의 엑셀 생성

### 1.3 현재 제공하지 않는 기능

법인 관리 웹 UI, 임베딩 필터, 자동 LLM API 호출, 자동 스케줄, CRM 연동, 기사 원문 일괄 수집은 구현하지 않았다. 조직 원본 엑셀 템플릿을 읽어 채우는 기능도 현재 범위에 포함돼 있지 않다. 이전 계획 중 재결정이 필요한 항목은 11절에 기록한다.

### 1.4 실행 환경

법인 리스트 원본은 업무망 Excel에 있다. VBA 생성, 뉴스 수집, 검토 결과 병합, 엑셀 생성은 개발·인터넷망 환경에서 실행한다. 망 간 파일 이관은 담당자가 조직의 승인된 절차로 수행한다. 법인 리스트는 변경 시 갱신하며 뉴스 수집 때마다 다시 추출하지 않는다.

## 2. 운영 순서

1. 법인 리스트가 변경되면 VBA를 생성하고 업무망 Excel에서 실행한다.
2. 즉시 창에 출력된 팀별 목록을 인터넷망으로 이관해 CSV로 정리·검증한 뒤 기준 CSV를 교체·커밋한다.
3. 모듈 2는 GitHub Actions에서 주말·공휴일을 포함해 매일 01:15 KST에 자동 실행된다. 수동 트리거로 기간을 지정해 다시 수집할 수도 있다.
4. 수집이 성공하면 LLM 검토 워크플로가 이어서 돌아 검토 배치를 판정·병합·정리한다.
5. 같은 워크플로가 모듈 3으로 엑셀을 생성해 JSON과 함께 커밋한다. 연휴 다음 첫 영업일에는 연휴 합본 엑셀도 만든다.
6. 담당자는 커밋된 엑셀을 확인한다. CRM 등 다른 시스템에는 담당자가 수동으로 옮긴다.

실행 명령은 각 모듈 README에서 관리한다.

## 3. 용어

| 용어 | 이 시스템의 의미 |
|---|---|
| 관리 법인 / 기존 거래 법인 | 기준 CSV에 등록된 법인. 자동 분류는 CSV 등록 여부에 따름 |
| 신규 후보 | 키워드 검색에서 관리 법인명이 확인되지 않은 기사. 실제 신규 법인 여부는 검토 전까지 미확정 |
| 신규 법인 | 검토에서 법인을 특정하고 신규 영업 후보로 채택한 항목 |
| 이슈 | 자동 선별 또는 검토를 통과해 `issues_by_corp`에 포함된 기사 |
| 영업시그널 | 기사에서 확인한 사건을 영업 검토 분야로 분류한 값 |
| 기준일자 | 결과 JSON의 `run_date`. 기사 수집 기간과 별도 |

CSV에 없다는 사실만으로 실제 거래 이력이 없다고 단정하지 않는다. 알파딜이라는 용어만으로 채택 여부를 정하지 않고 8절의 분류와 기사 내 구체적 사실로 판단한다.

## 4. 모듈 구성

| 모듈 | 입력 | 출력 | 실행 위치 |
|---|---|---|---|
| 1. VBA 생성 | 추출 설정, VBA 템플릿 | `.bas` 코드 | 개발 환경 |
| 생성된 VBA 실행 | 팀별 법인 리스트 엑셀 | 팀별 법인 목록 텍스트(즉시 창) | 업무망 Excel |
| 2. 뉴스 수집 | 기준 CSV, 검색 설정, 뉴스 응답 | 이슈 JSON, 검토 배치 JSON | 인터넷 연결 환경 |
| 검토·병합 | 이슈, 배치, 검토 결과 JSON | 갱신된 이슈 JSON | 담당자 작업 환경 |
| 3. 엑셀 생성 | 이슈 JSON | `.xlsx` | Python 실행 환경 |

모듈은 파일로 데이터를 주고받으며 각각 실행한다. 모듈 2는 기준 CSV를 직접 읽는다. 별도 서버나 웹 운영 리스트는 없다.

## 5. 처리 규칙

### 5.1 모듈 1 — 법인 리스트 추출

#### 5.1.1 추출 조건

기본 대상은 1팀~6팀 시트다. 시트명 공백을 무시한다. 법인명은 D열 4행부터 2행 간격으로 읽으며, 마지막 행은 D열의 마지막 값으로 정한다.

거래 확인 범위는 1~5팀 `DS:EA`, 6팀 `FE:FM`이다. 범위 안에 0이 아닌 숫자 값이 하나 이상 있으면 법인을 추출한다. 빈 셀, 0, 숫자로 판별되지 않는 텍스트는 조건을 충족하지 않는다. `excluded_labels`에 등록된 라벨은 제외한다. 현재 제외 라벨은 `수익`이다.

#### 5.1.2 출력

VBA는 즉시 창(Debug.Print)에 팀당 한 줄(`1팀 (N건) - 법인A, 법인B, ...`)로 출력한다. 즉시 창의 200줄 보관 한도를 넘지 않도록 팀 단위로 모은다. 담당자는 이 목록을 인터넷망으로 옮겨 `corp_name,team` 두 열의 CSV로 정리하며, 여러 팀에 속한 법인은 팀마다 별도 행으로 기록한다. 별칭 계산과 `_FOF` 제거는 모듈 2에서 수행한다. 추출 설정은 [모듈 1 config.json](../module1_vba_generator/config.json)에서 관리한다.

### 5.2 모듈 2 — 수집과 선별

#### 수집 기간

기본 기간은 한국 시간 기준 전일이다. 지정한 시작일과 종료일을 모두 포함하며, 기사 발행일을 한국 시간으로 변환해 비교한다. 날짜를 해석할 수 없는 기사는 제외한다.

최신순 응답을 페이지별로 읽고, 마지막 기사가 시작일보다 오래됐거나 응답이 한 페이지보다 적으면 수집을 종료한다. 현재 코드의 요청 한도는 검색어당 최대 10페이지이며 `start > 1000`이면 중단한다. 기본 페이지 크기는 100이다. 충분히 수집했는지 확인하지 못한 검색어는 `coverage_warnings`에 기록한다. 빈 응답 후에도 경고가 남을 수 있으므로 경고는 누락 확정이 아닌 확인 대상으로 해석한다.

#### 법인명 검색

1. CSV의 고유 법인명마다 등록명 그대로 검색한다. 별칭이나 `_FOF` 제거명을 별도 검색어로 사용하지 않는다.
2. 해당 법인의 검색 결과 안에서 제목 중복을 제거한다.
3. 제목과 description에서 법인명·별칭·정규화명을 지운 후 키워드를 센다. 법인명 자체에 포함된 단어가 영업 키워드로 잡히는 것을 줄이기 위한 처리다.
4. 키워드가 없으면 제외한다. 기본 설정에서 1개이면 검토 대상으로 보낸다.
5. 2개 이상이어도 원래 제목·description에서 법인명·별칭·정규화명을 확인하지 못하면 검토 대상으로 보낸다.
6. 나머지는 기존 법인 이슈로 채택하고 CSV에 등록된 모든 팀에 배정한다.

#### 키워드 검색

1. 설정의 키워드를 각각 검색하고 결과 전체에서 제목 중복을 제거한다.
2. 제목·description에 관리 법인이 매칭되면 이 경로에서는 제외한다.
3. 기본 설정에서 키워드가 2개 이상 매칭된 기사만 신규 후보로 보낸다.
4. 신규 후보의 법인명과 신규 여부는 검토에서 정한다. 자동으로 신규법인 시트에 넣지 않는다.

따라서 관리 법인과 미등록 법인이 함께 언급된 기사는 키워드 검색의 신규 후보에서 제외될 수 있다.

#### 키워드와 중복 판정

키워드는 대소문자를 무시한 부분 문자열로 매칭한다. 통과 기준은 그룹별 매칭 수의 합과 `weak_match_keyword_count`로 정한다. 기본값은 1이며, 이를 초과하면 키워드 조건을 통과한다.

가장 많이 매칭된 그룹을 대표 분류로 선택한다. 동률이면 설정에 먼저 나온 그룹을 선택한다. 출력의 `matched_keywords`에는 대표 그룹의 키워드만 남긴다.

중복 판정은 정규화 제목의 일치 또는 `SequenceMatcher` 유사도 0.82 이상을 기준으로 한다. 원문 링크가 있는 기사를 우선 선택하고, 같은 조건이면 `pubDate` 문자열 정렬의 첫 기사를 남긴다. 현재 구현은 실제 발행일이 가장 이른 기사를 보장하지 않는다. 법인 간·수집 경로 간 전체 중복 제거는 수행하지 않는다.

#### 요약과 검토

초기 요약은 description에서 HTML 등을 제거한 텍스트다. 15자 미만 또는 60자 초과이면 요약 수정 대상으로 보낸다. 긴 텍스트를 자동으로 잘라내지 않는다.

검토 배치는 기존 법인 판정, 신규 후보 판정, 요약 수정의 세 목록으로 구성한다. 요약 수정 목록에는 기존 법인의 자동 통과·판정 대기 기사가 포함된다. 신규 후보는 같은 목록에 자동으로 들어가지 않는다.

자동 수집 단계는 원문 본문을 읽지 않는다. 수동 검토 중 제목·description만으로 완결된 요약을 만들 수 없을 때는 원문을 확인할 수 있다. 판단과 요약 기준은 [검토 지침](../module2_news_pipeline/llm_review/prompt_template.md)을 따른다.

### 5.3 모듈 3 — 엑셀 생성

신규법인 시트를 맨 앞에 두고 1팀~6팀 시트를 생성한다. 열은 법인명, 이슈요약, 영업시그널 카테고리, 키워드, 원문링크의 5개다.

1행은 기준일자, 2행은 열 제목이다. 상단 2행을 고정하고 자동 필터와 원문 하이퍼링크를 적용한다. 법인별로 묶고 법인별 최신 기사 발행일 내림차순으로 배치한다. 같은 법인 안에서도 발행일 내림차순으로 정렬한다. 데이터가 없는 시트에는 `해당 없음`을 표시한다.

여러 팀 소속 법인은 모든 해당 팀 시트에 표시한다. 신규법인 시트에는 `corp_status`가 `신규`인 항목을 넣는다. 검토 완료 여부와 수집 경고는 엑셀 생성기가 검사하거나 표시하지 않는다.

## 6. 운영·검증 기준

- NFR-1. 모듈 2(뉴스 수집)는 GitHub Actions에서 주말·공휴일을 포함해 매일 01:15 KST에 자동 실행하며, 같은 워크플로우를 수동 트리거로도 실행할 수 있다. LLM 검토·병합과 모듈 3(엑셀 생성)은 수집에 이어 자동으로 실행된다. 주말·공휴일에 수집한 결과는 날마다 검토하고, 연휴 다음 첫 영업일에 하나로 합친 합본을 함께 제공한다. 모듈 1은 담당자가 수동으로 실행한다.
- NFR-2. 업무망과 인터넷망 사이의 파일은 승인된 절차로 이관한다.
- NFR-3. 현재 엑셀은 기본 레이아웃을 사용한다. 조직 원본 템플릿 적용은 11절의 결정 대상이다.
- NFR-4. LLM 검토는 담당자의 대화형 세션에서 수행한다. 파이프라인은 별도 LLM API를 자동 호출하지 않는다.
- 검토 목록의 모든 항목을 처리하고, 수집 경고를 확인한 뒤 엑셀을 확정한다. 현재 코드는 이 완료 조건을 강제하지 않는다.
- 코드 검증은 VBA 생성, 고정 응답 기반 뉴스 처리, 검토 결과 병합, 엑셀 생성 테스트로 수행한다.
- 실제 API 인증, 업무망 Excel 추출, 기사 선별 품질은 운영 환경에서 별도로 확인한다.

실행 시간·정확도·LLM 사용량의 수치 목표는 정하지 않았다. 측정하지 않은 항목을 충족한 것으로 표시하지 않는다.

## 7. 뉴스 API와 인증

[모듈 2 설정](../module2_news_pipeline/config.json)은 `hub`와 `legacy` 엔드포인트를 구분한다. 현재 기본값은 `hub`다. 인증정보는 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` 환경변수에서 읽는다. `.env` 자동 로딩은 없다.

요청은 검색어 하나, `sort=date`, 기본 `display=100`으로 보낸다. 응답의 `title`, `description`, `originallink`, `link`, `pubDate`를 사용한다. 호출 수는 법인 수뿐 아니라 키워드 수와 페이지 수에 따라 증가하므로 고유 법인 수를 일일 호출 수로 간주하지 않는다.

현재 클라이언트는 네트워크 오류와 HTTP 429에서 재시도하며, 다른 HTTP 오류는 예외로 중단한다. 부분 결과를 체크포인트로 저장하거나 중단 지점부터 재개하는 기능은 없다.

## 8. 키워드와 영업시그널

### 8.1 설정 기준

키워드 전체 목록은 [config.json](../module2_news_pipeline/config.json)의 `keyword_groups`에서 관리한다. 이 문서에 목록을 중복 기재하지 않는다. 분류명은 `keyword_group_to_sales_signal`의 값을 사용하며 LLM 검토도 같은 값을 사용한다.

현재 분류는 다음 9개다.

| 그룹 | 영업시그널 |
|---|---|
| 여유자금발생 | 여유자금 활용 제안(펀드/랩/신탁) |
| 조달니즈 | 조달 니즈 발생 |
| 파생결합상품 | 파생결합상품(ELB/DLB) |
| 담보대출유동성 | 담보대출/유동성 |
| FX솔루션 | FX 솔루션 |
| 퇴직연금 | 퇴직연금 솔루션 |
| 대체투자해외채권 | 대체투자/해외채권 중개 |
| 신사업제휴 | 신사업·제휴(콜라보) |
| 인사변동 | 인사 변동 |

`track1_only_keyword_groups`에 넣은 그룹(현재 `인사변동`)은 관리 법인 검색(트랙 1)에서만 쓴다. 키워드 전국 검색(트랙 2)에서는 검색하지 않고 신규 후보의 키워드 수에도 넣지 않는다. 트랙 1은 법인명 검색 결과를 로컬에서 거르므로 이 그룹을 늘려도 API 호출은 늘지 않는다.

관리 법인 검색어와 본문 속 이름 확인에는 법인격 표기(`(주)`, `주식회사`, `㈜` 등)와 `_FOF`를 뗀 이름을 쓴다(`classify_corp.compute_search_name`). CSV 이름 그대로 검색하면 "가람투자증권주식회사"처럼 표기가 붙은 법인의 기사가 거의 잡히지 않았다. 떼고 남은 이름이 3자 미만(`가람`, `나래`)이면 계열사 기사와 구분이 안 되므로 이름 확인과 신규 후보 제외에는 쓰지 않는다.

`track1_auto_pass`가 `false`(운영 설정)면 관리 법인 기사는 키워드 수와 상관없이 전부 LLM이 판정한다. 이름 확인과 키워드 2개 이상으로 자동 통과시키면 애널리스트 코멘트·통계 인용·계열사 기사가 판정 없이 들어온다(2026-10-01 배치 재현 결과).

`always_llm_review_keyword_groups`에 넣은 그룹(현재 `인사변동`)의 키워드가 걸린 기사는 키워드 수와 상관없이 애매 항목으로 보내 LLM이 판정한다. 인사 기사는 여러 인사 키워드가 한 기사에 겹쳐 걸리기 쉬워 키워드 수가 신호의 세기를 뜻하지 않기 때문이다.

이 분류는 검토 분야를 나타낸다. 기사만으로 해당 법인의 실제 상품 수요를 확정하지 않는다.

## 9. 데이터 형식

### 9.1 법인·팀 CSV

`corp_name,team` 두 열을 사용한다. 팀 번호는 문자열로 읽으며 현재 허용값은 1~6이다. 같은 법인·팀 조합을 중복 저장하지 않는다. CSV는 UTF-8 또는 UTF-8 BOM으로 읽는다.

데이터 출처와 갱신 절차는 [법인 매핑 README](../data/corp_team_mapping/README.md)에 기록한다.

#### 9.1.1 별칭

모듈 2는 `corp_alias_prefix_map`의 첫 일치 접두어를 치환해 별칭을 만든다. 예를 들어 `에스케이`로 시작하면 `SK`로 바꾼다. 별칭은 기사 내 매칭에 사용하며 별도 검색은 하지 않는다.

#### 9.1.2 `_FOF`와 해외법인

현재 `compute_base_name`은 설정 문자열 `_FOF`를 제거한다. 구현은 문자열 전체에서 해당 부분을 제거하며 접미사 위치만 검사하지 않는다. 매칭에는 제거명을 사용하고 출력·팀 배정에는 원래 법인명을 유지한다.

완전 영문 등록명도 그대로 검색한다. 모기업명이나 그룹 브랜드명으로 대체 검색하지 않는다. 이 방식의 변경 여부는 11절에서 결정한다.

### 9.2 이슈·검토 JSON

이슈 파일의 최상위 필드:

| 필드 | 형식과 의미 |
|---|---|
| `run_date` | 결과 날짜 문자열 |
| `collected_date_from`, `collected_date_to` | 실제 수집 기간 |
| `issues_by_corp` | 법인명을 키로 하는 이슈 배열 |
| `coverage_warnings` | `possibly_incomplete_corps`, `possibly_incomplete_keywords` 배열 |

각 이슈의 필드:

| 필드 | 형식과 의미 |
|---|---|
| `article_id` | 문자열. 같은 실행의 검토 결과 병합 키 |
| `title`, `summary` | 제목, 요약 문자열 |
| `originallink`, `link` | 원문·뉴스 링크 |
| `pub_date` | API 발행일 문자열 |
| `matched_keywords` | 대표 그룹의 매칭 키워드 배열 |
| `matched_corp` | 배정 법인명 |
| `corp_status` | 자동 통과는 `기존`, 신규 채택 후에는 `신규` |
| `team` | 팀 번호 문자열 배열. 신규는 빈 배열 |
| `keyword_tag` | 영업시그널 분류 문자열 또는 null |
| `needs_llm_polish` | 요약 수정 필요 여부 |
| `needs_llm_verdict` | 판정 필요 여부. 기존 법인 검토 통과 후 병합 시 필드가 제거될 수 있음 |

검토 배치는 `run_date`, 수집 기간, `ambiguous_existing_corp_issues`, `new_corp_candidates`, `summary_polish_needed`를 포함한다. 신규 후보는 이슈와 달리 `description`, `candidate_sales_signal`을 사용하며 법인 배정 전 상태다. 검토 결과 형식은 [검토 지침](../module2_news_pipeline/llm_review/prompt_template.md)에 정의한다.

### 9.3 엑셀 매핑

`matched_corp` → 법인명, `summary` → 이슈요약, `keyword_tag` → 영업시그널 카테고리, `matched_keywords` → 키워드, `originallink`(없으면 `link`) → 원문링크로 매핑한다. 시트 배치 규칙은 5.3절을 따른다.

## 10. 현재 제약

| 제약 | 운영상 처리 |
|---|---|
| API·페이지 한도와 키워드 밖 표현으로 기사 누락 가능 | 수집 경고와 실제 기사 표본을 확인 |
| 등록명·별칭의 부분 문자열 매칭으로 오탐 가능 | 검토에서 기사 주체와 법인을 대조 |
| 동일 매칭명이 여러 법인에 대응하면 조회에서 한 법인이 선택될 수 있음 | `_FOF` 등 충돌 사례를 11절에서 결정 |
| `article_id`는 Python `hash()` 기반이며 실행 간 동일성이 보장되지 않음 | 같은 실행의 이슈·배치·결과만 병합 |
| 동일 기사 ID가 여러 법인에 존재할 수 있고 병합은 ID로 조회 | 여러 법인이 연결된 검토 항목은 병합 전후 배정을 확인 |
| 병합을 반복하면 통과 기사가 중복 추가될 수 있음 | 한 실행의 결과는 한 번 병합. 재작업 시 해당 실행의 병합 전 이슈 파일 복원 |
| 병합기가 누락 판정·분류명·신규 법인명 등 결과 전체를 검증하지 않음 | 검토 결과를 담당자가 확인한 뒤 병합 |
| 신규 후보 요약은 자동으로 요약 수정 목록에 들어가지 않음 | 필요한 후보는 검토 결과의 요약 수정 목록에 추가 |
| 실행 환경 시간대에 따라 기본 `run_date`가 한국 날짜와 다를 수 있음 | 결과 날짜를 `--date`로 명시 |
| 즉시 창 텍스트와 Python 입력의 인코딩 차이 가능 | 이관 후 한글 표시와 UTF-8 인코딩 확인 |

이 절은 구현의 제약을 기록한다. 제약을 의도한 제품 정책으로 간주하지 않는다.

## 12. 문서 관리 기준

README는 실행 방법을, 이 문서는 처리 규칙과 데이터 형식을, 검토 지침은 기사 판단 기준을 관리한다. 규칙을 바꾸면 관련 코드·설정·테스트와 문서를 함께 갱신한다. 미결정 사항은 현재 동작과 구분하고 결정할 질문과 근거를 적는다. 과거 개발 대화나 환경을 현재 운영 상태의 근거로 사용하지 않는다.

## 13. 후속 기능

CRM 자동 연동, 팀별 대시보드, 정기 스케줄은 별도 요구사항으로 다룬다. 현재 일정이나 구현 약속은 없다.

## 14. 버전 관리

소스코드, 기준 CSV, 뉴스·검토 JSON, 확정 엑셀을 저장소에서 관리한다. 인증정보와 재생성 가능한 VBA `.bas` 파일은 커밋하지 않는다. 법인 추가·제외 이력은 기준 CSV의 Git 변경 내역으로 확인하며 별도 diff 스크립트는 사용하지 않는다.

GitHub Actions는 모듈 2 출력만 자동 커밋·푸시한다. 법인 데이터 갱신과 최종 엑셀 확정은 담당자가 커밋한다. 실제 제외 패턴은 [.gitignore](../.gitignore)를 따른다.
